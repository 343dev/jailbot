# 06 — Сохранять статус контейнера и корректно пересылать сигналы

**What to build:** automation получает точный результат контейнерной команды, а интерактивный пользователь может быстро и предсказуемо остановить реальную Docker-нагрузку через Ctrl-C или системный сигнал.

**Blocked by:** 01 — Создать строгий process-level контур тестирования CLI.

**Status:** done

- [x] Exit status успешно запущенной контейнерной команды проходит наружу без изменения для кода `0` и обычных ненулевых кодов.
- [x] `SIGINT` и `SIGTERM` пересылаются выполняющемуся Docker-процессу и приводят к различимым стандартным signal statuses.
- [x] Первый Ctrl-C быстро инициирует остановку, а поведение повторного Ctrl-C определено и не приводит к зависшему wrapper-процессу.
- [x] Cleanup ограничен по времени и не маскирует статус Docker или контейнерной команды.
- [x] После interruption не остаётся именованного контейнера, мешающего повторному запуску.
- [x] Терминальное управление выполняется только при подходящем TTY через терминальный канал либо удалено полностью; оно никогда не загрязняет `stdout` команды.
- [x] Process-level тесты посылают реальные `SIGINT` и `SIGTERM`, проверяют завершение, status и безопасный повторный запуск.
- [x] Документация фиксирует стабильную семантику exit status и сигналов без необходимости парсить сообщения об ошибках.

## Comments

Docker запускается как отслеживаемый child process. INT/TERM пересылаются, повторный сигнал форсирует остановку, wait повторяется после interruption и возвращает точный child status. Process-level тесты проверяют реальные сигналы 130/143 и успешный повторный запуск.
